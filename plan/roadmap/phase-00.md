# Phase 0 — Kickoff & the Stack of Abstractions

Intake, the sealed baseline viva, and the course map: every layer between a keypress and a pixel,
each tagged with the phase that opens it. Nothing here is taught at depth; the point is to see the whole
machine once, measure it once, and know where every later phase fits.
**Xref:** System Design (SD) 0.3.1–0.3.4 build the single-machine model at *design* level (processes vs
threads, the storage hierarchy, latency numbers). This course goes underneath every one of those
statements. `reference/numbers.md` here links to SD's numbers sheet instead of duplicating it.
**Reading:** CS:APP ch 1 (the tour), plus the toolbench setup.

## Cycle 0.1 — How a computer works, end to end

| ID | Type | Session |
|---|---|---|
| 0.1.1 | L | **The stack of abstractions** — Hook: "`hello.c` is 5 lines. Between you pressing Enter and 'hello' appearing, roughly how many distinct pieces of software and hardware are involved? Guess a number, then we'll count." · Derive: naive model "the CPU runs my program" → fails to explain why a program can't read another's memory, why `printf` output can vanish on a crash, why the same binary runs on different disks → the machine is a tower of abstractions, each hiding the one below behind an interface (ISA, syscalls, the file, the socket, the process) · Covers: transistors → gates → combinational/sequential logic → ISA as the hardware/software contract; microarchitecture vs architecture; the OS's three abstractions (process = virtualised CPU+memory, virtual memory, file = virtualised device) and why each exists; runtime/libc layer; compiled vs interpreted languages; what "abstraction" buys (portability, protection, concurrency) and what it costs (leaky abstractions: caches, page faults, TCP stalls show through); the four questions to ask of any layer (what does it hide, what does it promise, what does it cost, how does it fail); Amdahl's law first look; concurrency vs parallelism at thread/instruction/SIMD level; the course map (which phase opens which layer) · Probe: "Name one abstraction that leaks and how you'd notice." · "Why is the ISA the most stable interface in computing?" · "Is a VM an abstraction of hardware or of an OS?" · "Where does a Python program's `print` stop being Python?" · Anchors: draw the layer diagram from memory with one interface named per boundary; the ./hello trace (0.1.2) · Traps: *layer skipping* · Reading: CS:APP 1 "A Tour of Computer Systems" · File: `lessons/phase-00/0.1.1-stack-of-abstractions.md` |
| 0.1.2 | TR | **What runs when you type `./hello` and press Enter** — Hook: "Your terminal is idle. You type `./hello` and press Enter. List every hop until the pixels change. Who does each hop: hardware, kernel, a library, or a program?" · Path: key switch → keyboard controller/USB HID → interrupt → kernel input driver → terminal emulator (X/Wayland event) → pseudo-terminal master → line discipline (canonical mode, echo) → pty slave → shell's blocking `read` returns → parse → `fork` (task duplication, COW) → child `execve` (kernel loads ELF, maps segments, ld.so for shared libs) → `_start` → libc init → `main` → `printf` fills a stdio buffer → `exit` flushes → `write(1, …)` syscall → pty → terminal emulator → font rasterisation → GPU framebuffer → display; parent `wait`s, prints the prompt · Covers: each hop named and tagged with its phase (1 bits, 2 CPU/caches, 3 linking/ECF/Unix I/O, 4 processes/scheduling, 5 VM/COW, 6 concurrency, 7 devices/interrupts, 12 language runtime); where the program *could* block; which hops are syscalls; what `strace` would show; the difference between the process and the program · Probe: "Why does output appear if `hello` prints without a newline and exits, but not if it crashes?" · "Who reaps the child?" · "What changes if `hello` is statically linked?" · "What if the terminal is over SSH?" · Reading: CS:APP 8.4 (skim, preview only; read fully in Phase 3) · File: `lessons/phase-00/0.1.2-trace-hello.md` |
| 0.1.3 | LAB | **Toolbench & first measurements** — Hook: "How long does one iteration of an empty `for` loop take on this laptop? And one `getpid()`? Write your two guesses down in ns." · Predict: loop ns/iter at -O0 and -O2 (and whether -O2 deletes it); syscall count of `./hello` under strace; your L1/L2/L3 sizes before reading them · Build/Run: verify toolchain (`gcc`, `g++`, `gdb`, `valgrind`, `strace`, `ltrace`, `objdump`, `readelf`, `tshark`, `docker`, `openssl version`); optional installs (`perf`, `libasan libubsan libtsan`); `getconf -a pipe grep CACHE`, `lscpu`, `/proc/cpuinfo` (note the hybrid 6 P-core + 4 E-core CPU); write `labs/0.1.3-toolbench/loop.c` timing N iterations with `clock_gettime(CLOCK_MONOTONIC)`; build with `tools/run.sh`; run pinned to a P-core and an E-core with `taskset`; repeat 10× and report median and spread; `strace -c ./hello` · Measure: ns/iteration (median, min, max) per core type and opt level; syscalls of hello; cache sizes · Explain: why -O2 may make the loop vanish (dead-code elimination) and how `volatile`/an asm barrier prevents it; why runs vary (frequency scaling, turbo, interrupts, E vs P core); why min is often a better estimator than mean for microbenchmarks · Probe: "Your benchmark got 2× faster after the first run. Why?" · "How do you know you measured the thing and not the timer?" · Reading: — · File: `labs/0.1.3-toolbench/` |
| 0.1.4 | L | **Numbers from first principles** — Hook: "Someone claims main memory is 100× slower than L1. Another says 'reading from RAM is basically free.' Using only the speed of light, the size of a chip and how DRAM works, which one is closer and why?" · Derive: naive "memorise the latency table" → the numbers change every generation and the table can't answer 'why' → each number follows from physics and design: distance (signal propagation), capacity (bigger = slower lookup), technology (SRAM vs DRAM vs NAND vs spinning platters), protocol (a network RTT includes serialisation and queueing) · Covers: clock cycle at ~4–5 GHz; register/L1/L2/L3/DRAM latencies in cycles and ns with the reason for each (SRAM vs DRAM row activation, distance, associativity); DRAM bandwidth vs latency; NVMe 4K random read (~10–100 µs) vs sequential; HDD seek + rotation (~5–10 ms) derived from RPM; syscall (~100 ns) vs context switch (~1–5 µs); memory-page (4 KiB), cache line (64 B), disk sector (512 B/4 KiB), Ethernet MTU (1500 B); speed of light in fibre (~200,000 km/s) → Mumbai–Bengaluru, India–US RTT lower bounds; datacenter RTT (~0.5 ms); bandwidth-delay product preview; powers of two; how to sanity-check a claim with an order of magnitude · Probe: "Why is L1 not simply made bigger?" · "Why is random 4K read on an SSD slower than sequential?" · "What's the absolute minimum ping from Bengaluru to Virginia?" · "Why can a 10 Gb/s link still give you 50 Mb/s?" · Anchors: learner starts `reference/numbers.md` (≥ 20 entries, each with its reason), links SD's `reference/numbers.md` · Traps: *magic numbers* · Reading: Drepper 2007 "What Every Programmer Should Know About Memory" §2 (DRAM) · Xref: SD 0.3.2, 0.3.4 (design-level table; here, the derivations) · File: `lessons/phase-00/0.1.4-numbers-from-first-principles.md` |
